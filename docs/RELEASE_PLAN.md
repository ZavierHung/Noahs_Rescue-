# Noah’s Rescue：从本地原型走向发行

## 当前交付：0.2.0-alpha.1

这一版用于本地受控试玩，不是已上线产品，也不是可以直接公开邀请陌生人访问的服务。当前先解决“新玩家如何进入游戏，以及出错后能否继续”，保留既有玩法，不在本轮擅自制定房主独占权、商业模式或改变上帝判罚规则。

| 入口 | 使用者 | 行为 |
| --- | --- | --- |
| `/play` | 真实试玩玩家 | 一个本机身份，选择角色、按房间码加入、准备、游戏、查看本机参与记录 |
| `/mobile` | 开发者/测试组织者 | 六人同屏、一键安排六个独立测试身份、逐个模拟 |
| `/` | 原型调试 | 原有世界属性与上帝裁决台，保持可用 |

## 本轮已经实现

### 玩家进入与理解

独立玩家页面没有六人调试工具抢占主界面。复用现有方舟、神谕插画；玩法指南解释六个角色、集合开局、三维分数、手动召唤、行动汇报和人工确认奖惩。指南明确说明本地存档、模型数据发送与 AI 评估边界，不把 AI 建议呈现为线下事实。

等待室显示可复制的 8 位房间码，其他玩家选择空闲角色后输入房间码加入。完整 `GAME-XXXXXXXX` 和小写短码都可识别，错误格式在客户端阻止，房间不存在/席位冲突由后端拒绝。房间码不是密码，更不是授权令牌。

玩家刷新页面会恢复原角色及已关联游戏；“暂时退出”仍保留席位，加入才能重连。历史列表默认只显示本机记住的参与记录。注意这只是 UI 过滤，服务端仍未做房间读权限隔离。

### 弱网与数据一致性

建房请求有持久化防重复编号，先在本机身份存储，再发送给服务端。相同凭证与相同编号返回同一房间，即使先前回复丢失或服务端重启也不会重复建房。请求编号不能带着不同角色或前一局参数重复使用。新局创建和旧局归档在同一 JSON 事务完成；重试先查既有房间，不再次归档。

这覆盖普通建房、一键测试及创建下一局。客户端错误提示会区分未确认建房并提供“重试建房”；旧版没有请求编号的外部调用仍兼容，但不享受防重复保证。服务端内部编号哈希不会加入公共快照、玩家视图或上帝输入。

当前不承诺所有写接口都具备幂等：结算已有原有防重复保护；AI 异步任务与其他动作仍需后续完善。跨标签页创建两个不同请求会被视作两次真实建房。

### 工程与质量

- 独立 `GamePhone` 复用玩家页/模拟器，浏览器 HTTP 与存储访问抽到 `game-transport.ts`，核心流程仍在共享控制器和服务端。
- 网页和微信共用玩法指南、房间码校验与建房恢复逻辑；没有改写 `agent-loop.js` 或复制上帝流程。
- `npm run release:check`：检查产品版本一致、指定本地文件的忽略规则、Git 是否追踪指定凭证/存档文件、公共模板密钥是否为空，再执行完整测试/类型检查/构建/浏览器回归。不读取真实 `.env`，也不扫描或打印真实玩家档案。
- 新增 `.github/workflows/local-quality.yml`，未来推送/PR 可运行相同检查，使用 mock 模式、只读仓库权限，不要求模型密钥、不部署、不上传玩家存档。结构参考 [GitHub 官方 Node.js CI 文档](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)。该远端工作流尚未提交、触发或验收。

这个脚本是有限的文件与功能检查，不是完整密钥扫描、安全审计或上线许可。

## 发行阶段与验收门槛

| 阶段 | 必须完成 | 验收标准 |
| --- | --- | --- |
| 当前：本地 Alpha | 玩家入口、玩法说明、邀请加入、正常流程、错误恢复、回归门禁 | 六个独立身份可以开局并完成上帝流程；断网重试不破坏已保存数据 |
| 下一步：受邀远程内测 | 选定微信或 Web 身份体系、服务端认证、房间级读写权限、邀请管理、模型限流/额度控制、HTTPS | 未认证者不能读写；非房间成员不能查记录/任务或执行动作；恶意重复请求不能无限消耗模型 |
| 稳定性内测 | 事务型数据库、备份恢复、AI 任务持久化、写请求幂等、重启恢复、分页、日志脱敏 | 运行中断后无重复结算；恢复演练成功；并发和故障用例通过；日志不暴露密钥及私人文字 |
| 微信发行候选 | 真实 AppID/登录、开发工具与真机、弱网/后台/扫码、隐私与数据处理说明、合法域名及相应平台审核资料 | 在目标微信环境逐项验收，明确数据发送对象、保留及清理方式，再处理审核与发布 |
| 对外发行 | 明确产品规则、监控与告警、回滚方案、用户反馈与问题处理流程 | 发布清单经人工确认，具备异常停用模型/回退版本的方法 |

上表后续阶段是计划，不表示已经实现或符合平台审核条件。本轮没有提交小程序审核、创建云资源、注册域名、上线或推送仓库。

## 当前明确阻断公开访问的问题

1. 本地 `clientId` 是设备凭证，不是账号登录；房间读取、列表与 AI 任务查询缺少权限隔离。
2. JSON 仓库仅支持单进程，尚未具备生产数据库、备份轮换与恢复演练。
3. AI 任务存于内存，服务重启可能丢失进行中任务；没有用户级限流或额度限制。
4. `online` 表示显式加入/退出，不是可靠的网络心跳；默认任何在线成员都可改分、触发或结束游戏。
5. Web API 默认仍为 localhost，微信真机/HTTPS/域名/AppID 尚未验收。不要仅把监听地址改成公网地址就上线。
6. 完整微信隐私与审核资料必须结合实际运营者、数据保留策略、第三方模型与发布方式另行确认。

建议下一轮先确认目标发行形态，再实现“真实身份 + 房间访问控制”。这决定数据库的用户与成员关系，也应先于远程分享测试。

## 验证方式

```bash
npm run dev:mock       # 本地无真实模型的试玩服务
npm run test:quick     # 一键测试开局专项
npm run release:check  # 完整本地质量门禁
```

浏览器自动化把 `/api/` 请求转发到临时 HTTP 服务，实际跑房间服务和 JSON 持久化，不触碰用户运行中的 API 或存档，不读取 `.env`。微信接线测试模拟平台调用，不能替代微信真机验收。
