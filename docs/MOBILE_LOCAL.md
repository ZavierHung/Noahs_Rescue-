# Noah’s Rescue 手机端本地版

> 历史文档：本页描述已暂停的 0.2 小程序版本，源码与可运行环境保存在 `archive/miniprogram-v0.2`。当前 `feature/web-hex-map` 已与之解耦；请按 [网页 README](../README.md) 使用 `/` 和 `/lab`，以下旧入口与命令不适用于当前分支。

本次实现依据 `image/README/` 中六张 Demo。交付包括 **原生微信小程序** 和 **本地浏览器六人模拟器**，不是把网页放进小程序 WebView。两者共用同一份应用控制器、HTTP 接口、游戏规则和本地存档。原来的世界平衡台仍在 `/`，新体验在 `/mobile`。

0.2.0-alpha.1 增加独立玩家入口 `/play`，和 `/mobile` 的开发者模拟操作分开。共用 UI 已抽出到 `app/components/game/game-phone.tsx`，网页传输层位于 `app/lib/game-transport.ts`；不是复制第二套游戏逻辑。网页/小程序通过共享 `player-guide.js` 呈现玩法说明，通过 `parseRoomCode` 处理完整或短房间码。

## 先玩起来

在仓库根目录执行：

```bash
npm --prefix app ci
npm run dev:mock
```

打开 [本地手机模拟器](http://localhost:3000/mobile)。`dev:mock` 强制使用本地规则，不发送 LLM 请求，不需要密钥。已有开发服务占用 3000 / 8787 时先在原终端停止它，不要叠加启动第二套服务。

1. 直接点击顶部“一键测试开局”，无需先切换六人模式。
2. 程序安排六个独立测试身份，自动建房、加入、准备，并通过正常 API 执行开局校验。
3. 六个手机自动进入游戏页。可切回单人手机，通过顶部角色按钮轮流操作。上帝仍需手动触发。
4. 点击分数，拖动 1—19 滑条并填写调整原因。改变世界属性时沿用原灾难引擎。
5. 点击“触发上帝”，查看人设、神谕任务、初判与 RAG 依据。
6. 提交行动，例如 `已完成：两队共享物资，协作修复湿地，并记录了资源支出。`。无模型模式只做明确标注的规则判断，不能证明线下行动真实发生。
7. 可填写驳斥，再点击“听取最终裁决”。此时所有分数仍不变。
8. 查看奖惩数值预览，点击“确认并结算”才真正改分。同一裁决重复确认不会重复执行。
9. 下一回合或再次手动触发上帝；最后结束本局，在“记录”查看完整过程。暂时退出后，可回到原局。

“一键测试开局”使用单独的 `noah-quick-*` 身份；再次点击续接未结束的测试局，结束后再点才创建新局。“返回手动游戏”恢复原来的身份，不结束任何游戏。测试局也写入本地 JSON，不是临时预览。加入或准备部分失败可直接重试，同一局继续补齐。详见 [快速试玩与边界](QUICK_START.md)。

也可以使用原有手动流程：点击“六人同屏模拟”，点击“一键建房并准备六人”，再由任意手机点击“开始游戏”；或六个手机分别加入同一个 Game ID、分别准备。单人模式顶部可切换六个角色；每个角色保留独立本地凭证。要模拟“另一个设备抢占已占用角色”，使用独立浏览器配置或无痕窗口，应收到角色占用提示。

一键准备不会静默结束进行中的游戏。如果提示已有游戏，先结束旧局，或手动加入原等待室。

### 用已有 M3 接口

使用 `npm run dev`，沿用根目录 `.env` 的 MiniMax 配置。初判、行动评估、驳斥终判均使用同一个适配器，默认 `MiniMax-M3`；旧配置 `MiniMax-M3.0` 自动映射到这个官方型号名。任一阶段失败时显式降级为本地规则。界面会区分模型输出和规则输出。

密钥只放根目录 `.env`，**不放小程序、浏览器代码或 `config.js`**。`.env*`、运行期房间 JSON、开发工具私人配置已忽略。示例 `.env.example` 没有密钥。本次自动测试没有调用真实模型，也没有输出或修改已有密钥。

## 导入微信开发者工具

1. 本地 API 保持运行。开发者工具导入仓库下的 `miniprogram/` 文件夹，类型为小程序。
2. 项目提供游客 AppID `touristappid` 用于本地尝试；若工具要求，使用你自己的测试 AppID，并将个人项目配置留在忽略的 `project.private.config.json`。这里没有代注册、发布或审核。
3. 开启 ES6 转换；本地设置关闭合法域名校验（项目设置 `es6: true`、`enhance: true`、`urlCheck: false`）。
4. `miniprogram/config.js` 默认连接 `http://127.0.0.1:8787`。这是公开的 API 地址，不是模型地址。
5. 编译后，可直接点选角色进入，也可用 `wx.scanCode` 扫描普通二维码。二维码内容应为 `A01` 至 `A03` / `H01` 至 `H03`，或者 `noahs-rescue://role/A03` 等。程序不执行二维码 URL，不接受其他任意链接。
6. 小程序也可点“一键测试开局”，通过测试面板切换六位角色进行操作；“返回手动游戏”可恢复原身份。需要同时看到六个手机时使用浏览器模拟器。浏览器和小程序存储空间独立，一键开局各自创建/恢复本端测试房间，不冒用另一端席位。交叉联调时手动加入共同房间，选择空闲角色。

项目是原生 `App + Page + WXML + WXSS + wx.request`。页面内八种显式视图对应角色确认、加入、等待室、游戏、汇报/裁决、记录、详情、结束；退出用原生确认弹窗。共享控制器使用 ES Module，由微信开发者工具的 ES6 编译处理。

### 真机边界

手机的 `127.0.0.1` 指向手机自身，不是电脑。局域网真机调试时，手动将 `.env` 中 `GAME_API_HOST` 改为 `0.0.0.0`，将小程序 `API_BASE` 改为电脑的局域网地址，并处理微信开发工具、调试模式及防火墙要求。不要将无鉴权的本地 API 暴露到公网。正式发布前必须接入 HTTPS 合法域名、微信登录和服务端权限校验。

当前环境未安装微信开发者工具，未执行官方 WXML 编译、微信模拟器点击、真机扫码或真机网络验收。已执行 JS 语法、配置/事件绑定、页面生命周期 mock、共享流程 HTTP 测试、真实 Chrome 网页操作、Web 构建和类型检查；不能等同于微信真机验收。

## 模块与数据流程

```text
微信小程序 WXML/WXSS       浏览器六人手机模拟器（React）
             \             /
        共享应用控制器 miniprogram/shared/client.js
             │ 角色凭证、房间指令、轮询更新
        房间 HTTP 接口 + 可轮询 AI 任务
             │
        Room Service（状态机、成员校验、同房间操作队列）
             ├─ Rules：1—19、开局门槛、数值预览、幂等结算
             ├─ Tasks：五类任务，内容来自数据后端
             ├─ 原 Agent Loop（原流程未替换）
             └─ Room Repository → 本地 rooms.json
```

上帝流程仍然是：

**游戏状态 → 随机上帝 → 数据后端完整人设 → 本地 RAG → 初判 → 汇报/评估 → 驳斥 → 最终裁决 → 数值预览 → 人工确认执行。**

初判输入在原有 `round / attributes / activeDisasters` 基础上补充：Game ID、两队三维分数、六个角色状态、最近 20 条行动、当前桌游任务及结算规则。完整人设仍从 `server/data/god-prompts/` 读取，`god.md` 依然只是设计说明；不自动同步，不把提示词原文或哈希写入快照。

汇报评估使用同一位上帝的最新数据后端人设、触发时状态快照、同一组 RAG 证据和任务完成标准。汇报及评估结果作为证据进入原 `agentLoop.rebut`；玩家不驳斥也必须经过终判。每次神谕仍只提交一次最终驳斥，但一局可以重复手动触发多次独立神谕。

`server/data/tasks.json` 提供生态修复、合作、资源管理、平衡、反思五类示例任务。选择规则位于 `rooms/tasks.js`：优先照顾失衡中的低维度；三维接近时按回合选择平衡或反思。任务内容修改在下一次触发时生效。任务安排为当前回合完成，未结算不能推进回合；没有后台倒计时或额外 0—9 风险轨道。

### 试玩奖惩规则（明确的产品假设）

Demo 未提供完整数值公式，因此单独实现 `tabletop-v1`，不从模型自然语言中解析并执行加减分：

| 最终裁决语气 | 世界分数 | 发起本次神谕的阵营分数 |
| --- | --- | --- |
| reward | 环境 +1 | 社会 +1 |
| penalty | 环境 -1 | 经济 -1 |
| mixed | 环境 +1 | 经济 -1 |

数值在 1—19 截断，触及边界时预览可能为 `19 → 19`。上帝的叙事奖惩、线下措施不产生额外隐式改分；唯一执行依据为数值预览。汇报完成与否是终判的证据，不绕过上帝直接结算。若修改正式游戏规则，替换 `rules.js` 中 `POLICY / proposalFor` 并提高版本，同时更新测试。

多人权限假设：本地没有额外房主身份；同一局的在线成员都可手动改分、触发神谕、汇报、提交最终驳斥、确认奖惩和结束本局。每次操作记录角色和时间。这是桌面协作试玩机制，不是适用于公开竞技环境的权限方案。

### 一致性与恢复

- 六个角色固定、两队各三人；同一房间的同一角色不可被另一凭证占用。
- 同房间操作顺序执行，不同房间的 LLM 请求可以并行；仓库的文件锁只覆盖短事务，不在模型等待期间持有。
- 手动改分必须携带 `scoreRevision`，过期修改被拒绝。神谕未结算时锁定分数和回合，避免裁决依据变化。
- 奖惩基于服务端保存的提案；前端不能上传任意结算分数。按神谕 ID 幂等，重启后也不会重复扣分。
- JSON 采用临时文件加原子替换；`rooms.json` 有 `schemaVersion: 1`，未知版本拒绝读取。不要同时启动多个进程写同一目录。
- 退出不删角色和游戏；等待室退出会取消准备。`online` 目前表示显式加入/退出状态，不是网络心跳；关闭应用不自动释放席位。
- 浏览器/小程序存储只保存本地身份与上次房间 ID，权威分数、会话、事件都在后端 JSON。清除客户端存储会失去原身份，不能伪装原玩家抢回角色；可新建房间继续测试。
- AI 接口立即返回任务 ID，客户端轮询完成结果。内存任务 15 分钟后可过期；重启会丢失尚未完成的任务，但不会写入半份裁决。先刷新核实是否已存档，再重试，不直接重放整段操作。
- 结束本局会归档未完成的神谕，但不执行未经确认的奖惩。新局独立 Game ID，不覆盖旧记录。
- 建房携带持久化 `requestId`；同一客户端凭证和同一请求只对应一个房间。客户端在发请求前保存，明确成功才清理，网络/服务端失败则保留以供恢复。服务端把作用域哈希及原参数写入房间内部元数据，不通过公共快照或模型输入返回。
- 玩家入口只显示本机记住的参与房间，这是使用体验优化，不是服务端鉴权；原 API 仍可列出本地全部房间，不允许因此将服务公开。

## 接口契约

| 方法 | 路径 | 返回 |
| --- | --- | --- |
| GET | `/api/roles` | 六个角色 |
| GET | `/api/rooms` | 房间及记录，去除客户端凭证 |
| POST | `/api/rooms` | 创建房间；可带 `previousGameId` 原子归档旧局，`requestId` 用于持久化防重复 |
| GET | `/api/rooms/:id` | 单局完整快照 |
| POST | `/api/rooms/:id/actions` | 执行动作；AI 动作返回 `202 { jobId }` |
| GET | `/api/room-jobs/:id` | running / done + result / failed + error |

创建及动作请求都携带 `{ roleId, clientId }`。动作 `type`：`join`、`ready`（ready 布尔值）、`start`、`score`（scope/dimension/value/reason/scoreRevision）、`trigger`、`report`（judgmentId/text）、`rebut`（judgmentId/text，可空）、`settle`（judgmentId）、`advance`、`finish`、`leave`。

客户端凭证仅是本地身份隔离工具，**不是微信身份认证**。本地各房间记录均可查看。目前轮询返回完整存档，数据增多后应提供房间摘要、分页历史和增量事件。

## 测试与迭代

```bash
npm test                  # 原有测试 + 房间、任务、M3适配、原生接线测试
npm run test:multiplayer  # 真实本地HTTP + 六个共享控制器，完整跑完一局
npm run typecheck         # TypeScript
npm run build             # Web 构建
npm run check             # 全部自动测试、类型检查和构建
npm run test:e2e          # 浏览器操作：六人完整游戏、手机布局、准备失败
npm run test:quick        # 快速开局专项：真实 HTTP + 真实浏览器
npm run check:all         # 上述全部检查 + 浏览器测试
npm run release:check     # 本地内测质量门禁，不代表通过公开发布验收
```

所有测试使用临时目录/模拟模型，自动清理自己的数据，不改实际存档、不消耗 MiniMax 额度。六人测试覆盖加入、准备、开局、触发、跨阵营汇报、驳斥、人工结算、同步、退出重连、结束、下一局和历史查看。其他测试覆盖 1—19 边界、角色冲突、五人不能开局、离线不能开局、旧版本分数拒绝、重复结算、反复触发、跨房间并发、失败后继续操作、数据后端任务以及小程序事件接线。

本轮追加了真实浏览器自动化以及异步、重连、页面销毁和部分准备失败的回归检查。浏览器测试首次使用需要在仓库根目录执行 `npm ci`；详见 [2026-09-19 测试迭代记录](TEST_ITERATION_2026-09-19.md)。

建议迭代顺序：

1. **当前本地纵向切片**：用六人同屏验证玩法，收集任务、裁决口吻和数值反馈。
2. **微信运行时验收**：导入开发工具，逐屏核对 Demo，验证真机触摸、扫码、切后台和弱网；再决定是否加入语音输入。
3. **正式玩法**：产品确认数值公式、房主/确认权限、任务时限和断线规则；修改相应规则与契约测试，不改页面里的隐藏分支。
4. **服务端升级**：保持 service 接口，替换 repository 为事务数据库；增加微信登录、房间访问控制、幂等请求 ID、任务持久化、分页和自动迁移；最后再接服务器部署。

尚未包含：微信登录/支付、语音录入和转写、生产鉴权、云部署、真实语义向量模型升级。RAG 延续原本的本地 Hash-256 测试检索器，M3 是裁决模型，不是 embedding 模型。
